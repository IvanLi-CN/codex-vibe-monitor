# Retention Uses Task-Local Batches and Monthly Archive Target Files

Status: Accepted

## Decision

The calendar month is an archive destination and grouping key, not a Managed Task boundary. A Task Run selects a bounded set of eligible source rows, groups compatible rows for the same dataset and month, and completes each selected batch within that run. The run does not need to drain the month.

Each batch is closed in the same Task Run by producing or updating the canonical monthly archive target, verifying the artifact and source identity, and committing the corresponding source-row transition. Temporary work files are task-local and are removed at the end of the run. A later run selects remaining live rows again; it does not depend on unfinished staging, a continuation cursor, or an unfinished prepared artifact from an earlier run.

The existing monthly destination remains the canonical path generated by `archive_batch_file_path`: `archives/<dataset>/<year>/<dataset>-YYYY-MM.sqlite.gz`. A later eligible batch for the same dataset and month updates that same destination through the existing atomic replacement protocol. No new main-database columns or tables are required.

The retention budget is a design input. The planner must choose a batch scope and archive work shape expected to fit the configured run budget, including file preparation, verification, and the short source transition. Runtime timeout is a safety fallback only. Repeated timeout or routine reduction to tiny batches is an implementation defect, not an acceptable steady state.

This decision refines the catch-up behavior in ADR 0027: automatic catch-up may schedule another run for remaining live rows, but an unfinished staging artifact or continuation cursor is not the normal input to that run.

Normal-load acceptance is expressed as service rate rather than a minimum batch count. With approximately 30,000 invocation rows per day and 1.2 upstream-attempt rows per invocation, the candidate must sustain enough committed rows to catch up the fixed backlog while exceeding arrival by a wide margin. The initial capacity target is at least 50 times the corresponding arrival rate: approximately 17 invocation rows per second and 21 upstream-attempt rows per second, measured separately. Online request latency and SQLite safety remain gates; the target cannot be met by an unbounded transaction or by bypassing admission control.

Prompt-cache materialization and task observation remain separate derived maintenance. Their asynchronous state does not block a completed retention batch and does not change the immutable Task Run result.

Online writes must also avoid historical-key scans in the synchronous short working-set projection. Recent source rows use the existing key/time index; older in-flight candidates use the existing live invocation IDs plus the current mutation ID. Source key, time and display status are rechecked in the same SQLite snapshot, including when the working-set trigger runs before the live-ID trigger. This preserves working-set semantics without moving conversation-history statistics into retention transactions. Existing trigger definitions are repaired atomically by inspecting schema metadata, preserving deployed migration completion facts and adding no main database table, column or state value.

## Consequences

- A single run should process many rows and may update several monthly targets, but it is not required to finish an entire calendar month.
- The writer must amortize monthly-file preparation across the rows selected in the current run; one-row rewrites are a defect signal.
- A timeout leaves the current incomplete batch uncommitted and its temporary files removed. Completed batches remain final facts.
- Capacity validation must report committed rows per second, arrival rate, timeout frequency, file I/O, lock waits, and online p95/p99 separately for each dataset.
