# PostgreSQL 迁移直接写入业务表

目标库是新服务直接运行的数据库，实际数据库大小必须不超过 30,000,000,000 字节。压缩备份大小不能替代该验收指标。迁移不能通过删除业务数据满足容量约束。

## 存储边界

业务表只保存源业务列，使用源业务主键和唯一索引；不生成 `_cvm_payload`、`_cvm_run_id`、`_cvm_source_key` 或对应的冗余主键。迁移账本只保留对象定义、批次范围、行数、摘要、源快照身份和游标，不保留完整行数据。一个目标数据库对应一个迁移运行；另一个源或试验使用独立数据库。

首次导入把 SQLite 一致性快照按业务主键分页，以原生列类型分批 `COPY` 直接写业务表。一个批次的数据与 checkpoint 在同一 PostgreSQL 事务提交。全部数据写完后创建业务唯一索引、外键并校准 sequence。整行 JSON 只在客户端编码及计算摘要时短暂存在，不写入目标库。

## 最终追平与续跑

旧服务停止后，CLI 对其最终一致性快照开始新的业务主键游标扫描，不假设源端存在覆盖全部数据库变更的日志。目标端只创建一批原生列临时数据：按业务主键插入新行、更新确实变化的行，并删除已完整扫描主键范围内源端不存在的行；扫描完成后清理尾部删除。游标与写入同批提交，暂停后可以继续扫描。临时批次在事务结束时删除，不保留全量中间表。

没有业务主键或包含 NULL 主键的源表无法使用严格递增的键游标，此类表直接重放最终快照，仍不保存第二份持久数据。恢复时继续其已提交批次。外键在追平开始时移除，在完成全部表的同步后重新创建并校验，避免不同表加载顺序造成暂时的不一致。

每个扫描阶段记录不可变源快照的 SHA-256。续跑必须使用同一快照，不能把较新的线上快照与已提交游标混合。导入过程中断留下 `seeding` 或 `catching_up` 时，`resume` 可进入对应恢复阶段。CLI 通过数据库级 advisory lock 排斥并发迁移命令。

## 校验与容量

严格校验重新读取对应快照，按批次将期望的原生列写入临时表，与目标数据进行双向 `EXCEPT ALL` 比较，同时检查总行数、sequence、唯一索引和外键。该校验不能因为行数相同就忽略内容变化，也不依赖已清空的 staging。首次导入内部校验复用同一源快照；线上源继续写入不影响该快照。

每批提交后检查 `pg_database_size`，完成后再次检查。`MIGRATION_MAX_TARGET_BYTES` 可设定更小预算，不能超过 30,000,000,000；超限以失败记录退出，不输出验收通过。数据库大小检查不包括共享集群的 WAL、源快照或备份文件，部署仍须为这些独立文件留出空间。

## 既有试验库

迁移账本结构版本为 11。包含旧 `imported_rows` 的目标库明确拒绝继续导入，避免自动删表、重写已有结果或混用两种布局。保留旧库作为测量基线，以同一 SQLite 快照导入新目标数据库。该处理只涉及隔离试验库，不操作生产数据库。

旧版程序不保证读取新布局，因此持久状态影响按 minor 评估；HTTP API 保持兼容。源 SQLite 仍按原结构读取，不修改源库。上线资格必须由新布局的完整数据校验、运行时读写、实际容量及耗时证据共同确认。

## 隔离回归入口

`.github/scripts/verify-direct-pg-migration.py` 使用项目实际 CLI 与 PostgreSQL 18 测试库验证失败批次续跑、主键游标追平、同数量内容篡改、二进制数据、无主键和 NULL 主键、容量拒绝及 PG-only API 重启读写。调用方预先创建空的 `cvm_direct_test*` 数据库，通过受保护环境传入 libpq `PG*`、两种角色的连接配置和 `CVM_MIGRATION_BIN`。脚本拒绝使用非测试名称或已有业务表的数据库，不创建或删除数据库。
