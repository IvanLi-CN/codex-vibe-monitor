## Task Detail Metrics

- `src/maintenance_store.rs` defines per-task measurement capabilities and the additive `workloadTrend` detail response. It merges persisted samples with confirmed legacy managed attempts, deduplicates by execution UID and task key, fetches the persisted running attempt separately from the latest completed history, reserves response capacity for it and the in-memory running snapshot, returns at most 100 attempts in run order, and leaves pre-upgrade metric values unknown.
- `managed_task_work_runs` stores one monotonic sample per `(execution_uid, task_key)` in the maintenance database. Recorder notifications reuse the bounded asynchronous timeline queue; terminal samples force a final snapshot. Startup marks unconfirmed running samples unknown and rebuilds malformed sample JSON as an identity-preserving unknown record, sequence checks reject stale updates, recorder loss is represented as a coverage gap, and cleanup preserves the latest 200 terminal samples per task plus every running sample. Detail responses continue to expose at most 100 samples.
- Retention records an exact eligible invocation-row snapshot at run start, distinct eligible candidates, and rows only after their archive transaction commits. Other roots and the 16 startup-backfill children expose only task-specific units with proven semantics; truncated scan counts and mixed `processedCount` values remain unsupported.
- Committed-work notifications are scoped to the managed task identity. Compression records completed files, manifest refresh records completed archive batches, rollup materialization records batches after transaction commit, and archive pruning records each finalized deletion. Later failures therefore retain successful work without mixing units between nested maintenance operations.
- Child workload insertion applies the same terminal-overlay pruning as root insertion while preserving every running sample; durable recent-100 history remains in maintenance storage. Account-activity coverage repair publishes cumulative bucket counts immediately after each successful transaction commit. Its terminal guard reads that shared sample, so a later bucket failure, preemption, or unconfirmed cancellation retains committed work without double counting the final successful outcome. A failed repair is finalized before retry-progress persistence can fail.

## Catalog execution visibility and workload diagnosis

### Diagnosis baseline

The following observations describe the pre-implementation failure mode and remain useful when interpreting older records; they are not the current catalog contract.

- The catalog currently displays task identity, enablement, trigger mechanisms, effective policy, and execution class. Neither `ManagedTask` nor its list response supplies a latest-run summary; obtaining every full detail response would also fetch progress and workload history that the catalog does not need.
- `task_measurement_capabilities` declares all three workload metrics for `retention_archive`, only processed work for 22 tasks, and no workload metrics for 14 tasks. The unsupported group includes dashboard reconcile, timeline snapshots, long-term projection, account maintenance, and subscription refresh. Workload capability is independent of execution success.
- A minimal render of the actual `TaskWorkloadTrend` component with one successful attempt and three unsupported capabilities produces three “不适用” legends, “暂无计数”, no value series, and the “单位未知” chart frame. Repeating the same input reproduces the empty presentation. Changing only processed capability and its measurement to a valid observed zero produces one value series and removes the empty-count hint. This proves the local presentation problem; it does not establish that a deployed instance lost collected metrics.
- The backend distinguishes `not applicable`, `some metrics unknown`, recorder coverage gaps, and no recorded attempts. The chart's empty-count hint currently collapses several of those cases into “暂无计数”. Compatibility attempts deliberately retain missing historical counters rather than deriving them from mixed legacy `processed_count` values.
- Actual execution timestamps and monotonic duration are already stored in `task_timeline_segments` and the `managed_task_runs.actual_*` fields. Legacy `started_at` can be request time, and legacy `duration_ms` can include dispatcher waiting. A catalog execution summary must preserve this distinction instead of relabeling the existing detail fields.
- Detail workload responses and storage retain only the latest 100 terminal samples per task, plus running samples. The timeline retains a 48-hour buffer and permits 24-hour reads, but its current pagination covers all tasks and all segment kinds. Passing `limit=200` does not select the latest 200 executions of each task.
- The current successful roots with processed capability explicitly record their task-specific result, including zero. A separate Retention path needs a targeted regression before making a defect claim: pending and discovered can record zero while processed remains unobserved when no archive group commits. Failed or interrupted work and uncertain completion must not be converted to a fabricated zero.

### Agreed catalog behavior

- Every directory row should show the latest trigger time, execution duration, and result, including unsuccessful attempts rather than only the latest success. The latest-run summary is independent of the background chart's 24-hour window.
- Each row should use its background to show the observed pending population, discovered candidates, and committed work for individual attempts in the preceding 24 hours, matching the task-detail workload chart. Keep at most the latest 200 data points per task; retain the omitted earlier portion as empty space in the same time window. The owner selected workload counts as the vertical metric; execution duration remains in the latest-run summary and point details.
- Background charts should load lazily for visible rows. Data retrieval and chart mounting both need a bound; loading all task-detail histories before deferring only the drawing does not satisfy the requested performance behavior.
- Workload absence needs an explicit reason. Unsupported counters, no attempts in the window, incomplete collection, historical unknowns, and request failure cannot all mean “no successful execution”. Known execution outcomes must remain visible even when counters are unavailable.

### Catalog acceptance boundaries

- Latest-run metadata should load as one bounded catalog summary, independently of chart visibility. A run older than 24 hours still supplies the latest summary; no known run displays “尚无运行记录”, while unavailable observation displays “观测未知”. Actual running elapsed time must come from a fresh runtime observation and stop extrapolating when that observation becomes unknown.
- A background uses a fixed rolling 24-hour time axis. Select the latest 200 attempts for each task, then position the retained points at their actual times without stretching them to fill the row. Mark the earlier omitted range as a display limit, separately from no activity and collection gaps. A point outside the time window is excluded; the 201st point removes only the oldest displayed attempt.
- Background areas use the same raw-value, unit, scope, coverage, and subset rules as `REQ-TASK-OPS-010` and `REQ-TASK-OPS-012`. Plot only supported observed metrics, retain true zero on the baseline, and interrupt a series at missing evidence or a unit/scope change. Do not replace missing workload with duration, execution counts, or inferred zero. The task's identity dot retains its identity color; area colors continue to identify the three workload metrics independently of execution outcomes.
- The workload source needs a task-scoped, bounded 24-hour query and storage sufficient to preserve each task's latest 200 recorded attempts plus active observations. Deduplicate by execution identity before applying the response cap of 200 points, including current attempts in that cap. Existing detail views retain their recent-100 run-order behavior and 20/50/100 controls. Recent-run counters lost under the previous 100-sample storage limit remain a historical coverage limitation rather than being reconstructed from business data.
- Include authoritative success, partial completion, failure, cancellation, interruption, running, and confirmed skipped attempts when those outcomes exist. Queue requests and routine eligibility checks without an execution attempt remain distinct. Unknown start or duration stays unknown; confirmed skips do not acquire fabricated execution durations. Stable execution identities prevent duplication between persisted and current observations.
- A row entering the viewport initiates bounded history retrieval and mounts its background. Offscreen rows do not mount charts or subscribe to complete task-detail histories. Re-entry reuses valid cached data, concurrent work is bounded, and existing runtime/timeline revision signals refresh visible data without per-row fixed-interval polling. The background must not reduce text readability, obstruct the row link, or change row height while loading.
- Point inspection should expose trigger/attempt time, actual start where known, actual duration, outcome, trigger source, and a bounded reason. Desktop, narrow-screen, dark/light themes, loading, failure, no activity, coverage gaps, exactly 200 attempts, and more than 200 attempts require focused acceptance coverage during implementation.

## Rollout Facts

- The timeline adds idempotent columns and tables to the maintenance SQLite database. Existing `started_at` and `duration_ms` fields keep their request-time meanings; old rows do not receive reconstructed execution intervals. Existing enablement and schedule overrides are preserved.
- Computed policy fields are response metadata; reads do not rewrite `interval_secs`, `cron_expr`, or `next_trigger_at`.
- Unsupported existing overrides remain visible and can be cleared explicitly. Startup-only actions are not replayed by reset; their default behavior applies on the next process start.
- Observation writes use a bounded asynchronous channel and never write to the business database. Saturation or maintenance-store failures surface as coverage gaps.
- Workload samples are stored in a separate additive maintenance table; old task history is read only as attempt identity and never receives inferred P/D/C values. The task detail endpoint does not issue a business-table count or file walk to build a chart.
