## Coverage / rollout summary

- The endpoint is additive and read-only. It captures invocation and attempt row watermarks as one logical `asOf`/fence, reads the bounded timeline source projection in page-sized short read transactions on independent SQLite connections, resolves each page's fallback accounts in the same transaction, and hydrates the runtime account overlay in the first page transaction before closing the connection. The source scan and per-page materialization are capped by the scan budget, and the same captured fence applies to every page, projection, and account-hydration batch. Live materialization also carries the accepted dashboard generation/revision fence through every page and aborts before publication if the mutable runtime/source projection changes. It then publishes the bounded result into short-lived SQLite snapshot rows with a short `BEGIN IMMEDIATE` transaction using bounded multi-row batches. No source connection or read transaction is held across the full traversal, so a live source drift cannot be mixed into a published snapshot. Snapshot entries expire after 30 minutes; a bounded cache rejects new first-page anchors when full instead of evicting a cursor that may still be in use.
- The timeline request carries the selected natural-day UTC bounds separately from the viewport. The server rejects scopes and viewports wider than 24 hours, clamps persisted and live boundary overlap to the preceding 24 hours, and keeps the existing 30-day duration safety check separate from query range selection. This prevents a short viewport from scanning a 30-day history while preserving long terminal durations for calls that begin inside the selected day.
- Each materialized snapshot has explicit row and serialized-payload budgets, and the active cache has aggregate row and byte budgets. Exceeding any budget returns the timeline's unavailable state and rolls back the partial snapshot; it never truncates the result, samples rows, or mounts the legacy aggregate chart.
- Once the client has successfully traversed and merged every page for an `asOf`, it sends an idempotent `DELETE /api/stats/invocation-timeline/{asOf}`. The server immediately removes that token's in-process row/byte reservation and queues its durable rows for the existing 60-second P2-pressure-gated cleanup. The queue is bounded; overflow leaves rows for the normal bounded cleanup scan, and the 30-minute TTL remains the fallback for interrupted traversals, client-side page failures, or process loss. Release errors are diagnostic only and do not prevent the completed snapshot from being committed by the client.
- Materialization failures and canceled first-page requests use the same reservation-release and cleanup queue path. Their request guards do not perform synchronous or detached SQLite deletes; a canceled, incomplete traversal remains pageable only until its token is released or its TTL expires.
- Snapshot capacity rejections are classified by active-token, per-snapshot row/byte, and aggregate row/byte limits. Background cleanup logs active snapshot count/row/byte usage, queued release depth and overflow count, and each rejection counter so capacity exhaustion can be separated from query or database failures.
- The target `totalCount` path mounts `DashboardInvocationTimeline` without a legacy chart prop. Loading, unavailable, stale, disconnected, and pagination errors remain inside the timeline surface; non-target metrics and ranges keep the aggregate chart.
- The live hook traverses every page with one `asOf`, merges records by `(invokeId, occurredAt)`, releases the server reservation only after a complete successful traversal, and coalesces revisions while a request is in flight. A client-side page failure or incomplete merge leaves the `asOf` recoverable until TTL instead of blocking failure handling on cleanup. SSE revisions and the 15-second poll share one scheduler with at most one traversal in flight and one automatic traversal per rolling 15-second interval; traversal spacing and retry deadlines use the same browser clock, with a small timer guard against sub-millisecond scheduling variance.
- Failed traversals retain and freeze the last good snapshot, then retry after 15, 30, and 60 seconds with ±20% jitter, capped at 60 seconds. A successful traversal resets retry state. A retry can continue during SSE disconnection; ordinary revision-driven updates wait for the live connection to recover. User viewport and scope changes still load immediately.
- The live hook keeps the requested viewport separate from one atomically committed `{data, window}` snapshot. Automatic live-window advances continue rendering that committed pair until the replacement succeeds; a failed refresh leaves it visible and stale. User zoom/pan and natural-day/account context changes clear the committed pair and show loading for the new scope, while a local-midnight boundary alone does not reset the live timeline.
- A completed automatic traversal now commits its self-consistent `{data, window}` result even when the live viewport advanced while the request was in flight. The newer target is coalesced into one follow-up traversal after the existing 15-second scheduler gate, so a slow snapshot cannot permanently discard every completed response while the viewport keeps moving.
- Persisted timeline materialization uses a dedicated source row instead of the full `ApiInvocation` projection. It selects only timeline state, timing, concurrency, failure, and payload-account fields; invalid payload accounts are resolved from attempt rows in bounded batches of 100 keys while retaining the captured attempt watermark. The public endpoint, `asOf` contract, page cursor, deduplication, overlap bounds, and snapshot publication budgets remain unchanged.
- The live runtime overlay, live revision, and invocation/attempt watermarks are captured inside one stable-generation fence with up to four retries. A runtime projection or revision change during capture or later page materialization aborts before a mixed snapshot can be published. Runtime account hydration runs in the same short-lived source transaction as the persisted projection and fallback accounts, so a terminal transition cannot mix an old running overlay with a later database account. The accepted live revision is stored with the internal snapshot fence, preventing a slow materialization from adding runtime records newer than the `asOf` source boundary.
- Each materialization emits a fixed-field `invocation timeline materialization summary` with global/account scope, outcome, total elapsed time, materialization-lock wait, capture time, source connection and `BEGIN` time, source pages and scanned rows, materialized/published rows, source SQL time, account-resolution time, in-memory materialization time, source commit/close time, publish time, publish-coordinator wait, publish pool-acquire time, `BEGIN IMMEDIATE` time, publish SQL/commit time, publish batch count, and published rows. Active phase timers are finalized on cancellation; the summary intentionally excludes account values, payloads, and snapshot tokens.
- Dense lane bodies preserve 8–16px bar heights and a fixed 1px gap inside the existing 320px desktop / 336px compact frame. Once the minimum height no longer fits, only the lane body scrolls; the calls axis stays synchronized, and virtualization renders visible rows plus two rows of overscan. The total call count and row positions remain intact, with no sampling or horizontal scrolling.
- Snapshot cleanup runs as a shutdown-cancellable background task after HTTP readiness, first after 60 seconds and then every 60 seconds. It uses the database pressure gate, a non-blocking P2 admission, and a non-blocking materialization-lock check; busy passes are skipped. Each pass handles at most 48 explicit releases and reserves at least 16 of its 64 candidate slots for the periodic database scan, so a saturated release queue cannot starve reclamation of overflowed or expired rows. It reads the active-token registry after scanning, so a token registered during the scan is either absent from that pass's candidates or present in the active set before deletion. Cleanup deletes expired/non-active tokens by equality, allowing old-process rows to be reclaimed without a schema change or holding the materialization lock across database operations. When the managed-task scheduler owns this maintenance task, the legacy worker skips its pass and obtains the named task's execution lease before cleanup, preventing overlap with dispatcher-triggered runs.
- Today's dashboard activity revision triggers an authoritative timeline refresh; a bounded polling refresh keeps bars current between revisions. Yesterday remains HTTP-only.
- The first HTTP snapshot is allowed even when the live SSE connection is unavailable. After a successful snapshot, disconnection freezes live extension until reconnect; an initial failure remains an unavailable state inside the timeline surface.

- The local online observability baseline was unavailable because this worktree has no configured Grafana/CVM read credentials; no online p95 was inferred or recorded. The current local fixture acceptance passed with 20 complete materializations per scope over 7,000 global rows, including 5,000 valid calls and 2,000 malformed-payload fallback calls with two attempts each: global p50/p95/max was 922/2,537/2,741 ms, and account 42 over 3,500 rows was 713/1,182/2,629 ms. The existing `LiveRefreshPending` and `LiveRefreshStale` Storybook states remain semantically valid and require no new story; the focused hook/activity/demo suite passed 84 tests.
