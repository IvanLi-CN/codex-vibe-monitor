# Contention metric contract

The observability release adds measurements only. SQL, indexes, retry policy, scheduling, batch sizes and published projection algorithms stay at the observed baseline. The subsequent performance release consumes the same measurements and query definitions.

## Producer interface

`src/observability/contention.rs` owns fixed enums and per-runtime cached handles. Module producers import `observability::contention::*` and call `ObservabilityRuntime::count_performance(PerformanceCounter, u64)`, `observe_performance(PerformanceHistogram, Duration)` or `set_performance(PerformanceGauge, f64)`. The interface does not accept request-derived names or labels. Disabled collection returns before registration. Export reads recorded state only; no SQL, directory traversal or additional source polling runs during scrape.

Code without an `AppState` parameter obtains the scoped instance with `current_performance()`. Parent-owned HTTP, managed-task and writer entry points establish `with_performance(metrics, future)`; an explicitly spawned task must establish its own scope. Missing scope disables observation rather than binding a global runtime or changing business results. Independent tests use their own runtime and scope. Module instrumentation reports additional entry points to the integration owner so scope coverage is verified.

`observe_query(StatsQuery, future)` wraps one existing SQL execution future and preserves its exact result. It records success/error or a cancelled lower-bound duration on Drop, using the current instance scope. It must not wrap an entire projection containing file IO or add a query of its own.

`long_term_overlap` measures the canonical interval-state SELECT with `interval_start_ms < end` and `interval_end_ms > start` in `load_long_term_projection_interval_index`. Status reads and daily/rollup queries do not share this identity, so their cheap executions cannot dilute the overlap latency distribution. Empty or invalid date sets do not execute or count that SQL.

| Module               | Event or state                                                          | Meaning                                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Retention            | `RetentionBatch(operation, outcome)`                                    | One actual finished/deferred/error/cancelled batch, never a proposed batch                                                                                   |
| Retention            | `ProcessedRows(operation)`, `ArchivedRows(operation)`                   | Reuse `cvm_maintenance_processed_rows_total` / `cvm_maintenance_archived_rows_total`; increment only after commit, once at the owning boundary               |
| Retention            | `RetentionPhase(operation, phase)`                                      | Actual monotonic elapsed time; `write_hold` includes overlapping source/delete/commit work and must not be summed with them                                  |
| Retention            | `RetentionBacklog(operation, kind)`                                     | Existing inventory's actual record count or oldest pending UTC timestamp; absent observation remains unknown                                                 |
| Backfill             | `WakeNotification(task, decision)`                                      | Incoming new/merged/disabled/stale notification, distinct from a database attempt                                                                            |
| Backfill             | `WakeAttempt(task, outcome)`                                            | Actual wake confirmation attempt: committed/noop/busy/locked/error/cancelled                                                                                 |
| Backfill             | `Wake(task, state)`                                                     | Per fixed task pending indicator, first outstanding obligation UTC timestamp and next due UTC timestamp; duplicate notifications retain the oldest timestamp |
| Maintenance database | `StoreWrite(operation, outcome)`, histogram `StoreWrite(operation)`     | Independent database write outcome and actual elapsed time, without mixing main database BUSY/LOCKED                                                         |
| Summary              | `SummaryResponse(result, reason)`                                       | success/degraded/unavailable and a bounded reason; histogram is split by result so fast failure cannot improve successful p95                                |
| Statistics           | `Query(query, outcome)`                                                 | Fixed Summary, prompt-cache statistics and long-term overlap query observations independent of dynamic hotpath SQL slots                                     |
| Projections          | `ProjectionLastGood(projection)`, `ProjectionPending(projection, kind)` | Published proof timestamp and actual known dirty-bucket/source-gap/row counts; sequence differences are not counts                                           |

Task labels come only from the existing 16 `StartupBackfillTask` variants. New labels use only `operation`, `phase`, `outcome`, `task`, `query`, `reason`. A producer must report a missing observation as absent, not zero. Once an observer has established an empty backlog it may publish zero count and zero timestamp; dashboards mask the timestamp when pending is zero. Timestamps let Grafana calculate age and due delay without scrape-side work. Restart resets in-memory observations and is annotated in comparisons.

A pending wake observation represents a notification awaiting durable wake/control confirmation, not all unfinished business backfill. A matching confirmation clears the covered observation; a failed confirmation retains it, and an older confirmation cannot erase a newer notification. An in-memory scheduler wake alone is not durable confirmation. Ordinary business task results do not recreate or clear this observation; business work remains described by the existing dirty/progress facts. Observation tickets are bounded by the fixed task enum and do not change scheduling generations, retries or execution.

Projection freshness advances only at successful publication. A Prompt Cache database baseline that is published as a new frame or reused with identical payload establishes a last-good timestamp; health reads, retained last-good responses, in-memory deltas and failed rebuilds do not renew it. Source-specific pending fields report actual known units and are not interchangeable with sequence differences or identity counts.

Retention `write_hold` is owned by the admitted write permit, from successful admission through its release, including any intervening artifact recheck and post-commit cleanup. `transaction` separately measures begin through normal commit or explicit rollback completion; errors and cancellation record the observed lower bound and do not prove the native worker has drained. File verification, source verification, transaction, delete, commit and cleanup can overlap the hold or one another and must not be added. A selected batch that stops partially because of its deadline or cancellation reports deferred or cancelled, while already committed rows remain counted.

Histogram buckets preserve all 16 existing short buckets, add 200ms and 20/30/60/120/300s, and retain the 250ms, 1s and 10s boundaries. Budget exceedances use count minus the corresponding cumulative bucket, not sums of overlapping phases. Histogram series admission charges finite buckets plus `+Inf`, sum and count; the 3,996 application-series limit and separate hotpath allowance remain unchanged. Fixed handles are initialized only when observed and retain their bounded slot even when the global series budget refuses registration; refusal is visible through the existing degraded/drop signals.

## Comparison and collection quality

Recovery producers use `record_recovery(RecoveryDiagnostic)` at an observed boundary. `cvm_runtime_recovery_diagnostics_total` accepts only the enumerated `operation` and `reason` combinations in `src/observability/contention.rs`; it neither counts archived rows nor establishes task success. Invocation range admission, connection acquisition and transaction durations use `PerformanceHistogram::InvocationRange(InvocationRangePhase)`. A cancelled future records only observed elapsed time and never proves that native SQLite work released its ownership. Existing per-module outcome and committed-row counters remain authoritative. These observations reuse the instance scope and cached series budget; missing scope disables collection without changing business behavior.

Index diagnostics count actual metadata inspections by the existing explicit preparation command, including the read-only schema-inspection phase of `--dry-run`: `index_present`, `index_missing`, `index_definition_conflict`, or `index_unavailable`. The managed command can still write task-run metadata, so it is not a read-only production investigation channel. A successful later creation does not rewrite the preceding missing observation. They are neither a periodically polled index inventory nor proof of an execution plan; absent observations leave production definitions unknown. The owned inspector explicitly carries its caller's metrics scope. Export never invokes the command or repeats a metadata query.

During that explicit dry-run inspection of the conversation index, the owned connection also compiles `EXPLAIN QUERY PLAN` for the actual shared correlated statistics builder with one fixed empty key. It executes no business lookup and exports no parameter or plan text. `query_plan_indexed` requires the matching definition and a named-index SEARCH of the invocation alias in the observed plan; `query_plan_fallback` requires a successful nonempty plan without that proof. Missing query schema, compilation failure or the existing total deadline produces `query_plan_unavailable`, never a claimed fallback. The inspection shares the command's deadline and native cleanup owner; requests, startup and metrics export do not perform it. These counters describe inspection events, not a continuously verified production plan.

Grafana groups retention, background backfill, statistics and proxy/terminal protection. Every latency comparison includes result counts, completed work, backlog amount/age and collection health. Successful p95 below 100 samples and p99 below 1,000 samples are labelled low sample; missing series remain unknown. Existing cumulative runtime gauges are plotted as current readings, never Counter `rate` or `increase`.

Before/after windows pin UTC boundaries, application/image SHA, dashboard version, query version, configuration, restarts and task enablement. Report absolute values, per 1,000 completed requests and per 1,000 committed rows. Different workloads require stratified descriptive results, not an equal-load causal claim. Production receives no synthetic traffic. Two hours of naturally observed retention/backfill activity gate the fix deployment only; implementation, tests, review and readiness proceed while the baseline accumulates.

The `cvm-sqlite` dashboard groups the module observations before the existing coordinator and native SQL diagnostics. Quantiles and their sample gates use the same selected-window `increase`; the Summary gate displays insufficient p95/p99 samples separately from missing observations. `compare_offset` selects a fixed 1d or 7d offset with the same window length. An offset without history stays unknown. The offset is a descriptive comparison, not proof of matching load. UTC windows and deployment/configuration identities must still be recorded for an accepted comparison.

The proxy dashboard distinguishes running attempt records, confirmed identity-tracked terminal facts, replay/acknowledgement obligations and routing materialization duration. `cvm_proxy_confirmed_terminal_pending_records` and `cvm_proxy_confirmed_terminal_oldest_observed_age_seconds` reuse the existing identity registry: duplicate registrations preserve the first observation; a successful business commit stops the observation even when journal acknowledgement retries. They cover tracked generated invocation identities, not failed/unconfirmed acceptance. Restart recovery starts a new monotonic observation, so recovered age is a lower bound. The journal's existing pending records and terminal failure flag remain separate protection signals for recovery and unconfirmed acceptance. The legacy journal age is continuous nonempty time, potentially including running begin events; it must not be labelled terminal age. Routing's latest materialization duration is a batch duration, not terminal enqueue-to-commit latency. Existing cumulative gauges are not converted to event counters.

The preview provides `fixture`, `failures`, `low-samples` and `missing` instances without contacting production. `scripts/check-contention-dashboard.py --grafana-url <session-preview-url>` verifies the provisioned dashboard targets against Prometheus, validates result and sample gating, and compares equivalent classic/native SQL quantiles. The preview converts inspectable classic hotpath fixtures to native histograms with custom buckets using Prometheus's [documented conversion settings](https://prometheus.io/docs/prometheus/latest/configuration/configuration/); this fixture conversion does not alter production collection.

This observability release uses the owner-approved functional acceptance boundary: metric correctness, boundedness, business compatibility, regressions, Grafana evidence, required CI and formal review remain gates; the 5% overhead budget is explicitly unverified and is not a pre-release requirement. Any later overhead claim must use the trusted `main` GitHub-hosted `workflow_dispatch` path and the complete current REQ-016/016A contract: four parallel workload lanes (`runtime`, `pair-0`, `pair-1`, and `pair-2`), nine 60s measured windows with 60s warmup across the three pair lanes, distinct pair runner identities and compatible five-field hardware, unchanged stability/collection rules, and at most 5% CPU per completed request and successful p95 increase within the shared 60-minute test limit. Unavailable evidence is not a pass. Local and Agent VM pressure tests are prohibited. Grafana rendering may use provisioned synthetic fixtures in the conversation's single session-owned Agent VM; that visual evidence does not establish performance.
