# Contention metric contract

The observability release adds measurements only. SQL, indexes, retry policy, scheduling, batch sizes and published projection algorithms stay at the observed baseline. The subsequent performance release consumes the same measurements and query definitions.

## Producer interface

`src/observability/contention.rs` owns fixed enums and per-runtime cached handles. Module producers import `observability::contention::*` and call `ObservabilityRuntime::count_performance(PerformanceCounter, u64)`, `observe_performance(PerformanceHistogram, Duration)` or `set_performance(PerformanceGauge, f64)`. The interface does not accept request-derived names or labels. Disabled collection returns before registration. Export reads recorded state only; no SQL, directory traversal or additional source polling runs during scrape.

Code without an `AppState` parameter obtains the scoped instance with `current_performance()`. Parent-owned HTTP, managed-task and writer entry points establish `with_performance(metrics, future)`; an explicitly spawned task must establish its own scope. Missing scope disables observation rather than binding a global runtime or changing business results. Independent tests use their own runtime and scope. Module instrumentation reports additional entry points to the integration owner so scope coverage is verified.

`observe_query(StatsQuery, future)` wraps one existing SQL execution future and preserves its exact result. It records success/error or a cancelled lower-bound duration on Drop, using the current instance scope. It must not wrap an entire projection containing file IO or add a query of its own.

| Module               | Event or state                                                          | Meaning                                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Retention            | `RetentionBatch(operation, outcome)`                                    | One actual finished/deferred/error/cancelled batch, never a proposed batch                                                                                   |
| Retention            | `ProcessedRows(operation)`, `ArchivedRows(operation)`                   | Reuse `cvm_maintenance_processed_rows_total` / `cvm_maintenance_archived_rows_total`; increment only after commit, once at the owning boundary               |
| Retention            | `RetentionPhase(operation, phase)`                                      | Actual monotonic elapsed time; `write_hold` includes overlapping source/delete/commit work and must not be summed with them                                  |
| Retention            | `RetentionBacklog(operation, kind)`                                     | Existing inventory's actual record count or oldest pending UTC timestamp; absent observation remains unknown                                                 |
| Backfill             | `WakeNotification(task, decision)`                                      | Incoming new/merged/disabled/stale notification, distinct from a database attempt                                                                            |
| Backfill             | `WakeAttempt(task, outcome)`                                            | Actual wake confirmation attempt: committed/noop/busy/locked/error/cancelled                                                                                 |
| Backfill             | `Wake(task, state)`                                                     | Per fixed task pending indicator, first outstanding obligation UTC timestamp and next due UTC timestamp; duplicate notifications retain the oldest timestamp |
| Maintenance database | `StoreWrite(operation, outcome)`, histogram `StoreWrite(operation)`     | Independent database write outcome and actual elapsed time, without mixing main database BUSY/LOCKED                                                         |
| Summary              | `SummaryResponse(result, reason)`                                       | success/degraded/unavailable and a bounded reason; histogram is split by result so fast failure cannot improve successful p95                                |
| Statistics           | `Query(query, outcome)`                                                 | Fixed Summary, prompt-cache statistics and long-term overlap query observations independent of dynamic hotpath SQL slots                                     |
| Projections          | `ProjectionLastGood(projection)`, `ProjectionPending(projection, kind)` | Published proof timestamp and actual known dirty-bucket/source-gap/row counts; sequence differences are not counts                                           |

Task labels come only from the existing 16 `StartupBackfillTask` variants. New labels use only `operation`, `phase`, `outcome`, `task`, `query`, `reason`. A producer must report a missing observation as absent, not zero. Once an observer has established an empty backlog it may publish zero count and zero timestamp; dashboards mask the timestamp when pending is zero. Timestamps let Grafana calculate age and due delay without scrape-side work. Restart resets in-memory observations and is annotated in comparisons.

Histogram buckets preserve all 16 existing short buckets, add 200ms and 20/30/60/120/300s, and retain the 250ms, 1s and 10s boundaries. Budget exceedances use count minus the corresponding cumulative bucket, not sums of overlapping phases. Histogram series admission charges finite buckets plus `+Inf`, sum and count; the 3,996 application-series limit and separate hotpath allowance remain unchanged. Fixed handles are initialized only when observed and retain their bounded slot even when the global series budget refuses registration; refusal is visible through the existing degraded/drop signals.

## Comparison and collection quality

Grafana groups retention, background backfill, statistics and proxy/terminal protection. Every latency comparison includes result counts, completed work, backlog amount/age and collection health. Successful p95 below 100 samples and p99 below 1,000 samples are labelled low sample; missing series remain unknown. Existing cumulative runtime gauges are plotted as current readings, never Counter `rate` or `increase`.

Before/after windows pin UTC boundaries, application/image SHA, dashboard version, query version, configuration, restarts and task enablement. Report absolute values, per 1,000 completed requests and per 1,000 committed rows. Different workloads require stratified descriptive results, not an equal-load causal claim. Production receives no synthetic traffic. Two hours of naturally observed retention/backfill activity gate the fix deployment only; implementation, tests, review and readiness proceed while the baseline accumulates.

The controlled overhead gate uses the existing GitHub-hosted one-shot performance workflow: 60s warmup, 300s windows, three alternating pairs, existing stability/collection conditions and at most 5% CPU per completed request and successful p95 increase. An unavailable environment is not a pass. Grafana rendering is validated with provisioned synthetic fixtures in Agent VM; screenshots require explicit target/scope approval.
