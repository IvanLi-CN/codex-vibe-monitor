# Stats 长期用量与性能统计演进记录

## 关键决策

- 长期统计使用独立汇总表和独立 API，避免在现有 Stats 内容上叠加状态耦合。
- 日汇总永久保存，小时汇总保留默认 400 天且最少 366 天；所有清理动作以日汇总 materialized 为前置条件。
- 首次升级采用可恢复后台回填；回填未完成时只显示准备进度，避免把部分历史误报为完整结果。
- 完整汇总可以作为保留 continuity 的下界，但不能作为部分候选的更新来源；候选必须整体过滤后才能进入 UPSERT，避免被删除出重建集合的日期从 partial map 漏写。
- 历史 `overall` 日/小时与 canonical hourly rollup 不一致时，服务会持久化修复队列并从真实 live/archive 调用重建所有维度；canonical 的全量运营字段不能直接作为长期口径，只有排除 `running`/`pending` 且全部已完成调用 archive 均可读取时的终态证明字段用于验证。有界增量写入会把证明降为未完成，来源全量对账一致后才恢复可信；每小时审计都重新验证已完成 archive，即使先前所有桶均已认证，任一 archive 后续缺失或不可读时也必须撤销全部终态证明并进入 `error`，且对账结果不再包含的既有可信桶同样必须撤销证明，不能以剩余来源认证局部数据。来源可用性错误未消除前，每一次后续刷新都立即重试完整对账，避免恢复后仍等待一小时。升级新增证明列时，源数据不完整的旧 canonical 行必须保持未证明，不能将默认零值当作空日。canonical 空日是合法的零值证明，且任一维度的非零残留都会触发清理，零总量跨日墙时续段则必须保留。归档删除时，来源安全下界由真实调用的最晚墙时终点精确计算，并与 `cleanup_state=delete_pending` 在同一事务中持久化；归档继续保持 `completed` 可读，文件删除成功或确认不存在后才删除元数据，失败时留下可重试的删除意图。历史遗留文件若已在本轮开始前缺失，则只在既有 materialization、replay 与保留期门槛均已满足时完成元数据收尾，且不从 manifest 猜测来源下界。请求尝试归档的账号映射无法追溯到可读调用来源时必须保留归档。调用归档暂时不可读时，不再猜测一个固定跨日窗口，而是阻断其开始日及后续候选发布、保留最后已知行并通过既有 `error` 合同重试。
- 删除意图不能只按 manifest ID 延续：月度归档可在文件替换时复用同一行。收尾因此比较完整归档身份，并在立即 SQLite 事务中复核文件 SHA-256；writer 在替换前先撤销旧 `delete_pending`，防止清理线程删除新文件。
- API Key 删除保留稳定统计身份，凭据、会话和路由状态全部清除；其它上游继续使用原删除行为。

## 关联演进

- 长周期归档与 retention 约束沿用 `9aucy` 的 materialization/cleanup 边界。
- 请求阶段耗时、模型与 cache 字段沿用 `z9h7v` 的可观测性事实源。

## 实现落点

- 长期统计读取路径只依赖日汇总；archive 仅在后台回填阶段解压读取，并通过 `long_term_usage_stats` replay target 阻止未完成 archive 清理。
- `LongTermStatsSection` 把长期统计状态隔离在现有 Stats 之后，模型/账号表格共享固定列定义并分别启用行、列虚拟化。

## 本次演进
