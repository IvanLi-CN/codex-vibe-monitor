# Codex Account Pool Request-Body Streaming Survey

## Scope

This survey distinguishes two unrelated capabilities:

- Response streaming: an upstream or downstream Server-Sent Events response is delivered incrementally.
- Request-body live forwarding: the proxy starts writing the incoming HTTP request body to the selected upstream before it has received the client's EOF.

The second capability is the subject here. A proxy that buffers, parses, rewrites, spools, or replays a body before dialing the upstream does not provide end-to-end request-body live forwarding, even when it supports SSE responses.

## Findings

| Project                                                                                       | Account-pool evidence                                                                         | Request-body behavior                                                                                                                     | Result for native Codex traffic                                                                                                                                                    |
| --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [darvell/codex-pool](https://github.com/darvell/codex-pool)                                   | The project describes a pooled multi-provider account proxy.                                  | Its generic streamed path passes `r.Body` into the outbound request, and documents a no-retry direct-stream threshold.                    | Hybrid. Native Codex `/v1/responses` bodies are first transformed into a disk-backed temporary file and then replayed upstream. It is not end-to-end live forwarding on that path. |

Its SSE passthrough is response streaming only.                                                                                              |
| [digitalwm/openai-codex-oauth2-proxy](https://github.com/digitalwm/openai-codex-oauth2-proxy) | The README documents multiple auth files and round-robin rotation.                            | The Warp router uses `warp::body::bytes()` for every request, then the Responses handler parses the complete byte slice as JSON.          | Buffered before routing and sending. Its Responses response-streaming branch returns `501 Not Implemented`.                                                                        |
| [lilong7676/codex-pool](https://github.com/lilong7676/codex-pool)                             | The project documents a multi-account Codex manager and locally balanced compatibility proxy. | Its Axum HTTP handlers use `Json<T>` request extractors and convert the completed request into a proxy turn before scheduling an account. | Buffered and decoded before account selection. ## Evidence

- `darvell/codex-pool` documents `PROXY_MAX_INMEM_BODY_BYTES` as the direct-stream threshold in its [README](https://github.com/darvell/codex-pool/blob/main/README.md#L157). Its generic `proxyRequestStreamed` constructs an upstream request directly from `r.Body` in [main.go](https://github.com/darvell/codex-pool/blob/main/main.go#L3763-L3839). This is a genuine request-body streaming path, with no replay retry guarantee.
- The same project explicitly treats native Codex Responses requests differently: it transforms the body to a disk-backed representation in [main.go](https://github.com/darvell/codex-pool/blob/main/main.go#L1893-L1940). `streamCodexResponsesRequest` creates a temporary file, completes the lexical JSON rewrite, flushes, seeks back to zero, and only then returns that file for the upstream request in [streaming_responses_request.go](https://github.com/darvell/codex-pool/blob/main/streaming_responses_request.go#L281-L452).
- `MortalImmortality/CodexProxy` documents multi-account load balancing in its [README](https://github.com/MortalImmortality/CodexProxy/blob/main/README.md#L31-L44). Its Responses handler reads the whole request in [proxy/proxy.go](https://github.com/MortalImmortality/CodexProxy/blob/main/proxy/proxy.go#L1961-L1995), while its upstream call is built from a byte reader in [proxy/proxy.go](https://github.com/MortalImmortality/CodexProxy/blob/main/proxy/proxy.go#L281-L315).
- `digitalwm/openai-codex-oauth2-proxy` documents multi-account rotation in its [README](https://github.com/digitalwm/openai-codex-oauth2-proxy/blob/main/README.md#L3-L18). The router aggregates input with `warp::body::bytes()` in [src/main.rs](https://github.com/digitalwm/openai-codex-oauth2-proxy/blob/main/src/main.rs#L4307-L4327), and its Responses route rejects requested response streaming in [src/main.rs](https://github.com/digitalwm/openai-codex-oauth2-proxy/blob/main/src/main.rs#L4385-L4411).
- `lilong7676/codex-pool` documents multi-account balancing in its [README](https://github.com/lilong7676/codex-pool/blob/main/README.md#L5-L22). Its OpenAI and Anthropic handlers take `Json<T>` request extractors in [src/proxy/mod.rs](https://github.com/lilong7676/codex-pool/blob/main/src/proxy/mod.rs#L447-L520); the later SSE code therefore concerns the response, not the inbound request body.

## Conclusion

It is not supportable to claim that every open-source Codex account pool or relay lacks request-body streaming: `darvell/codex-pool` has a real generic direct-stream mode. It is likewise incorrect to interpret its name or README as proof that native Codex `/v1/responses` traffic is forwarded live before the full body is available.

Across the representative account-pool projects examined here, native Codex-compatible request paths that need body-dependent selection, protocol translation, hosted-tool filtering, retry, or replay are buffered or disk-spooled before delivery upstream. The sample cannot prove a universal negative for every repository, but it supports treating end-to-end request-body live forwarding for those Codex paths as an uncommon trade-off rather than an expected baseline.
